# 本 fork 的定制

上游 SurveyKing 只开源了后端，前端以编译产物的形式随仓库发布。因此这里的定制分两类：后端按上游包结构新增源码，前端在编译产物上做定点替换。

---

## 一、角色题库授权

按角色批量授权题库，入口在 系统管理 → 角色管理 → 题库授权。

授权关系记在新增的 `t_role_repo` 表。题库可见性本身仍然只认 `t_repo_partner`，所以授权时把角色下的用户展开写进 `t_repo_partner`，复用原有的可见性判断，不改动任何既有逻辑。撤销授权时反向收回；如果用户还通过别的角色持有同一题库，则保留。角色成员发生变动时用「同步」重新展开一次。

### 新增文件

| 位置 | 内容 |
|---|---|
| `server/api/src/main/java/cn/surveyking/server/api/RoleRepoApi.java` | 接口与页面入口 |
| `server/rdbms/src/main/java/cn/surveyking/server/domain/model/RoleRepo.java` | 授权关系模型 |
| `server/rdbms/src/main/java/cn/surveyking/server/domain/dto/RoleRepoRequest.java` | 请求体 |
| `server/rdbms/src/main/java/cn/surveyking/server/domain/dto/RoleRepoView.java` | 页面所需数据 |
| `server/rdbms/src/main/java/cn/surveyking/server/mapper/RoleRepoMapper.java` | Mapper |
| `server/rdbms/src/main/java/cn/surveyking/server/service/RoleRepoService.java` | 服务接口 |
| `server/rdbms/src/main/java/cn/surveyking/server/impl/RoleRepoServiceImpl.java` | 服务实现 |
| `server/api/src/main/resources/static/role-repo.html` | 独立管理页面 |

页面是独立 HTML，不进前端 SPA 的路由，因此不需要改动前端产物；它走同源 cookie 鉴权，接口全部用相对路径。

### 接口

| 方法 | 路径 | 权限 |
|---|---|---|
| GET | `/api/system/role/repo?roleId=` | `system:role:update` |
| GET | `/api/system/role/repo/counts` | `system:role:list` |
| POST | `/api/system/role/repo/save` | `system:role:update` |
| POST | `/api/system/role/repo/sync?roleId=` | `system:role:update` |
| GET | `/role-repo` | 已登录 |

### 建表

`t_role_repo` 的建表语句已并入 `server/rdbms/src/main/resources/scripts/init-h2.sql` 与 `init-mysql.sql`，新建库时自动创建。已有库需要手工执行一次对应的建表语句。

## 二、练习模式答题卡

### 现象

练习模式下答题卡的「已答/未答」计数恒为 0，格子全是未答样式；移动端更明显，答对和答错显示同一种颜色。

### 原因

表单 store 的 `computeProgress()` 负责给每道题算 `finished`，它在懒加载分支里提前返回（练习模式始终走懒加载），于是 `finished` 从来没被赋值。桌面端的格子另有 `correct`/`wrong` 两个类兜底，问题不明显；移动端的格子只有 `marked/finished/current`，样式表里也没有对错配色，缺陷就完全暴露出来。

### 改动

1. 懒加载分支返回之前，用 `form.values` 补齐每道题的 `finished`
2. 移动端格子补上 `correct`/`wrong` 两个类，样式表补上答对绿、答错红

## 三、怎么重放

前端改动落在编译产物上。`tools/frontend-patch.py` 按内容定位目标文件，不写死 chunk 名与哈希，因此换上游版本也能重放：

```bash
python3 tools/frontend-patch.py --static server/api/src/main/resources/static
python3 tools/frontend-patch.py --jar /path/to/surveyking.jar
```

脚本幂等，重复执行不会重复写入；必需的补丁点若没命中会直接报错，避免换版本后静默改错位置。

| 补丁点 | 定位依据 |
|---|---|
| 答题卡计数 | 懒加载分支里的 `void(this.progress=i/n);` |
| 移动端格子对错 | 格子样式类 `{marked:x,finished:y,current:z}` |
| 移动端配色 | `.adm-answer-sheet .answer-sheet-item.current` 规则 |
| 角色管理页入口 | 消息 id `pages.system.role.toolbar.new` 与工具栏「新建」按钮的写法 |

补丁里用到的模块别名（判空助手、props 变量、渲染函数）都从被改文件自身反推，不写死在脚本里。

## 四、构建与部署

上游公开分支是 v1.13.0，它的前端产物与更高版本并不相同，直接 `gradle build` 得不到与线上一致的系统。所以部署走「官方 jar + 增量」：

```bash
python3 tools/build-injected-jar.py --base .toolchain/surveyking-v1.13.2.jar --out dist/surveyking.jar
```

它依次做三件事：用官方 jar 里的依赖编译 `RoleRepo*.java`、把编译结果和 `role-repo.html` 打成 `role-repo-patch.jar` 注入 `BOOT-INF/lib`、再对 jar 内的前端产物跑一遍 `tools/frontend-patch.py`。

打包时补丁脚本会把改动过的分包换成新文件名，同步主包里的哈希映射，并按主包内容更新入口页的版本参数。这样升级后浏览器不会继续用旧缓存，旧文件名的条目也保留着，仍持旧主包的页面不会打不开。

`.toolchain/` 放两样东西：官方原版 jar（构建基线，必须是未打过补丁的那份）和 `lombok.jar`，两者都在 `.gitignore` 里，不随仓库分发。

服务器上保留一份本仓库检出，执行：

```bash
bash tools/deploy-server.sh            # 只拉代码并构建，产物在 dist/
bash tools/deploy-server.sh --deploy   # 替换 jar 并重启容器（中断约 15 秒）
```

默认只构建不重启，因为重启会中断服务，有人在答题时会受影响。
